# 02 — Производительность

Опора: production-сборка (Next 15.5), размеры бандлов из сборки, чтение кода. Реальных замеров Core Web Vitals на телефоне не было — это первый пункт (P1).

## Текущее состояние (из сборки)
| Что | Значение |
|---|---|
| Общий JS для всех страниц | 103 kB |
| Главная, первый заход | ~191 kB |
| Карта тела | ~186 kB (three.js грузится лениво, только здесь) |
| Supabase в браузере | только у вошедших, после отрисовки (сделано ранее) |
| Аудио в `public/audio` | 39 МБ (стримится по требованию, кешируется на месяц) |

## Находки

### P1-1. Повторные запросы к Supabase Auth за один показ страницы — P1, S
- **Проблема.** `supabase.auth.getUser()` вызывается в 11 файлах. Каждый вызов — сетевой запрос к серверу авторизации. На Главной за один показ это middleware + `getSessionUser` + `getMyProfile` + `getSocialCounts` + `countMyUnread` — 4–5 обходов, каждый 50–150 мс из Европы.
- **Решение.** Один кешированный на запрос `getAuthUser = cache(async () => (await createServerSupabase())?.auth.getUser())` в `lib/supabase/server.ts`, и все модули берут пользователя из него. Позже — переход на `auth.getClaims()` (проверка подписи JWT локально, без сети) после включения асимметричных ключей в Supabase.
- **Польза.** Минус 150–400 мс к ответу большинства страниц. Меньше нагрузки на бесплатный тариф Supabase.
- **Риск.** Низкий: тот же пользователь, только без повторов. Патч: `patches/P1-auth-cache.md`.

### P1-2. Нет кеширования публичного контента между запросами — P1, M
- **Проблема.** Все страницы динамические (из-за cookies авторизации), поэтому библиотека, программы, посты тренера и товары читаются из базы при каждом открытии каждым пользователем. `cache()` действует только внутри одного запроса.
- **Решение.** Публичные чтения (тренировки, курсы, авторы, посты тренера, магазин) через анонимный клиент и `unstable_cache(..., { tags: ["workouts"], revalidate: 300 })`; в серверных действиях админки — `revalidateTag("workouts")` после сохранения. Персональные данные (лайки, прогресс) остаются динамическими.
- **Польза.** Библиотека и Обзор отвечают за десятки миллисекунд, база почти не нагружается при росте пользователей (принцип Amazon: кешировать то, что одинаково для всех).
- **Риск.** Средний: надо аккуратно разделить публичные и персональные данные, иначе черновики админа могут попасть в кеш. Только анонимный клиент для кешированных функций.

### P1-3. Нет измерений на реальных устройствах — P1, S
- **Решение.** Включить Vercel Speed Insights (бесплатно на Hobby, без cookies) или `useReportWebVitals` с отправкой в собственную таблицу. Цели: LCP < 2.5 с, INP < 200 мс, CLS < 0.1.
- **Польза.** Оптимизации по данным, а не на глаз.

### P2-1. 197 отдельных наблюдателей прокрутки — P2, S
- **Проблема.** Каждый `<Reveal>` создаёт свой `useInView` (IntersectionObserver из `motion`). На длинных лентах это сотни наблюдателей и повторные рендеры при появлении.
- **Решение.** Один общий IntersectionObserver на страницу (модуль-синглтон) или CSS `@starting-style` / `animation-timeline: view()` с фолбэком. `motion` остаётся только там, где нужна физика (шторки, меню).
- **Польза.** Плавнее прокрутка на слабых Android, меньше JS при гидратации.
- **Риск.** Низкий, визуально без изменений.

### P2-2. Необработанные `<img>` (27 мест) — P2, M
- **Проблема.** Аватары, баннеры, фото постов и товаров отдаются в исходном размере (фото с телефона 3–5 МБ). `next/image` используется только в одном месте.
- **Решение.** Для изображений Supabase Storage — `next/image` с `remotePatterns` на домен проекта и `sizes`, либо Supabase Image Transformations (`/render/image/…?width=…`) — на бесплатном тарифе их нет, поэтому `next/image` (оптимизация на Vercel, лимит Hobby 1000 исходных изображений в месяц — достаточно на старте).
- **Польза.** В 5–20 раз меньше трафика на ленте и профилях, быстрее LCP.
- **Риск.** Средний: лимит оптимизаций Vercel; при превышении — переход на загрузку уже сжатых файлов (сжатие в браузере перед загрузкой, `canvas.toBlob` до 1600 px, WebP).

### P2-3. Сжатие изображений при загрузке — P2, S
- **Решение.** В формах загрузки (аватар, баннер, пост, товар) уменьшать фото в браузере до 1600 px и WebP ~0.82 перед отправкой. Это дешевле, чем оптимизация на сервере, и экономит хранилище Supabase (1 ГБ на бесплатном тарифе).

### P2-4. Аудио 39 МБ в репозитории — P2, S
- **Проблема.** Репозиторий и каждый деплой тащат 39 МБ; «Дождь» — 14,6 МБ одним файлом.
- **Решение.** Перекодировать в AAC 64 kbps моно (природа) и 128 kbps (музыка) — кодировщик есть в macOS (`afconvert -d aac`), в песочнице ассистента он недоступен; либо перенести файлы в Supabase Storage (публичный бакет `audio`).
- **Польза.** ~−60 % объёма, быстрее старт звука на мобильном интернете.

### P2-5. Шрифт Caveat почти не используется — P2, S
- Используется в 2 местах, но грузится на всех страницах (`next/font` добавляет preload). Либо убрать, либо подключать только на страницах, где нужен.

### Что не требует изменений
- three.js — только на `/body`, цикл отрисовки засыпает в покое.
- Модель скелета кешируется на год, аудио на месяц.
- Supabase-клиент в браузере не грузится у гостей.
